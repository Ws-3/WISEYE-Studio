## 最新可行性复评：移动盘和下载使用同一发布物

技术路线可行，适合继续实施，但当前尚未通过独立包构建验收。UE 已有 Game Target；Qt 有独立部署路径。已在编辑器中跑通的城市、飞控和传感器是功能基础，不等于 Shipping/Cook 已通过。首个里程碑应是基础场景的独立端到端包，再加入城市；无需先开发完整在线更新服务。

| 事项 | 可行性及尚需验证内容 |
|---|---|
| 用户不另装 UE/Python | 可实现；必须随包收齐 Game、Qt、Python/native DLL 和 worker 依赖，验证干净 Windows |
| 硬盘拷贝与网站下载 | 同一发布版本、文件清单与哈希；只改变获取渠道，不做两套仿真程序 |
| 本地安装后离线运行 | 推荐默认；资源齐备后启动不依赖网络或原移动盘 |
| 城市包独立下载 | 可设计；需验证通用资产归属、地图依赖和 Cook 容器的正确加载，不是简单移动现有文件夹 |
| 在线升级 | 可实现，尚未实现；先支持变更组件替换与回滚，再验证更细的资源补丁 |
| 保留现有功能 | 必须用独立包复测飞行、碰撞、云台、多设备、可见光/红外及 RTSP，不能只测试能打开窗口 |

实际主要风险按优先级为：① AirSim/CitySampleSupport 的非编辑器 Game 构建及运行；② 城市 Cook、动态加载资产和已知缺失引用；③ 当前借用 Anaconda 的桌面环境能否完整独立部署；④ 配置路径、进程启动和就绪握手的发布模式改造。前三项未跑通之前，不给出确定交付时间、最终体积或“任意电脑可运行”的承诺。

首版交付建议为完整离线安装目录（安装器与分卷资源），从硬盘拷贝或完整下载后安装到用户指定的本地 SSD。联网安装器随后复用同一组件清单，选择基础包/城市包并支持续传。安装源与运行目录分离；安装成功后移除安装源不影响运行。用户配置放本机可写目录，跨机携带航线/Fleet采用显式导入导出。

完整安装仍先按 25–60 GiB 规划，这只是此前的工程容量预算，未通过 Cook 实测。传输介质不改变体积；排除开发缓存、裁剪无用引用和合理场景分包才会减量。保留真实城市的同时，不应以删必要建筑/碰撞/材质来追求很小的包体。安装包下载大小必须在生成发布文件后单独统计。

验收门槛：在无 UE、VS、Python、Anaconda 的目标 Windows 上，从复制或下载的相同发布物安装，普通用户离线启动，完整飞行和传感器功能通过、配置可保存，拔除传输盘后仍可再次启动。城市持续运行至少 30 分钟，并记录加载时间、资源占用、预览延迟和实际包体。硬件性能仍决定流畅度，打包不自动消除预览链路延迟。

## 1. 结论

采用 Windows x64 独立 UE 仿真程序、现有 WISEYE 桌面程序和配套飞控/视频进程，通过一个启动入口管理。用户安装后双击运行，不需要另装 UE 编辑器、VS、Git、Python 或 Anaconda；安装器包含必要运行依赖并检测 VC++ 运行库。

支持设计为在线更新：界面程序、UE 仿真程序、基础资源、城市资源分别版本化，按兼容组合发布。修改界面不重下城市；应用更新在停止仿真并正常退出后生效，保留离线运行与离线升级入口。

现有工程还不是可交付安装包。不能把源码目录、`.venv` 或完整 UE 安装目录复制给用户，当成独立发布。

## 3. 包体预算与减量方法

当前运行的是 Small City 的 WISEYE 副本，不是 Big City。地图 `.umap` 自身很小，城市体积主要来自网格、纹理、材质及 World Partition 数据；不能仅统计地图文件。

以下是用来规划下载、安装和磁盘空间的早期工程预算，**不是实际 Cook 结果，也不是承诺的上下界**：

| 部分 | 暂定安装容量预算 |
|---|---:|
| 桌面、飞控、视频运行依赖 | 0.5–1.5 GiB |
| UE 运行程序及必要运行插件，不含场景资产 | 1–4 GiB |
| 基础场景和通用设备资产 | 0.2–1 GiB |
| 城市 Cooked 资源 | 20–50 GiB |
| 含城市的完整安装版本 | 先按 25–60 GiB 规划 |

未执行 Cook 前，不能可靠给出下载压缩率。Nanite、纹理、平台烘焙数据和压缩容器可能使结果与源文件大小明显不同。下载体积应由最终发布文件逐字节统计，不再用源工程大小推算。

空间建议：首次完整城市安装尽量准备 100 GiB 可用 SSD 空间；含城市的大更新及回滚按 120–150 GiB 空闲空间规划。实际更新器必须按“下载暂存 + 新版本展开 + 保留旧版 + 安全余量”计算，不采用一个固定阈值保证所有更新成功；用户另选的数据盘和录制文件另算。

减量次序：

1. 只 Cook 发布入口地图及依赖。保留城市副本需要的 World Partition/HLOD/FastGeo 数据，不同时发布原版演示城市入口和 WISEYE 副本。
2. 审计硬引用、软引用与字符串动态加载。Avata/Mavic、旋翼模糊材质、红外材质等通过代码加载的对象必须明确进入 Cook 清单，不能为了减体积漏掉。
3. 当前 Crowd 约 6.086 GiB、Vehicle 约 4.908 GiB，尽管生成器已移除，资源仍在开发目录。先通过 Cook 依赖报告判断哪些仍被引用，再决定是否重构引用；不能直接承诺省去这约 11 GiB，更不能直接删除源资产。
4. 不发布编辑器模块、源代码、PDB、Intermediate、原始 DDC、测试数据和开发日志；Shipping 需要的着色器/运行数据仍需正确生成。开发机文件本轮不删除。
5. 对 AirSim/Qt/视频工具按实际依赖裁剪。当前 SimLibs 中含约 263 MiB 的 CUDA ONNX provider，不能因为本机 Intel GPU 没使用它就直接删除；先审查链接、延迟加载和运行期导入，再决定是否随包分发。

首包必须产出四个数字：UE 程序及插件净体积、基础/城市容器净体积、全套安装后体积、实际下载字节数。此后用这四项替换本节预算。

## 4. 发布架构与用户操作

建议安装目录结构（名称为设计，不要求改现有 UE 模块 test/testEditor）：

```text
WISEYE/
  WISEYE.exe                 # 唯一日常启动入口
  Updater/                   # 独立更新与修复程序
  versions/<release-id>/
    Desktop/                 # Qt 界面及必要运行库
    Workers/                 # 飞控、RTSP 网关等独立入口
    Simulation/              # UE Game 程序、运行插件
    release.json             # 本次兼容组件组合
  content/<content-id>/      # 不可变的基础/城市容器集
  current.json               # 当前已验证版本指针
```

用户设备、航线、布局、参数、日志放 `%LOCALAPPDATA%\WISEYE\`，大体积录制目录由用户选择。默认配置只读随包提供，首次运行复制到用户目录。UE 与桌面通过统一配置根路径使用同一份可写设置，升级不覆盖用户文件。

从用户角度：安装 → 可选择下载城市组件 → 启动 WISEYE → 选择场景 → 开始仿真。已安装内容可离线运行。后台进程由主程序负责，显示“初始化/加载场景/飞控就绪/运行中/失败原因”，不让用户手动开多个控制台。

启动次序为：配置与版本检查 → 启动 UE Game → 等待场景、run_id 和设备起点确认 → 启动飞控 → 等待就绪 → 需要外部视频接口时启动 RTSP 服务 → 开放控制。维持现有独立飞控权威、按设备寻址和队列上限。

UE 场景进程只运行一份，多设备由 Fleet 管理。退出或更新时先正常停止控制与仿真，等待进程退出再换文件。画面 GPU 共享优化可独立接入，打包本身不消除现有 JPEG 显示链路延迟。

## 6. 在线更新设计

### 更新内容与单位

| 用户改动对应的版本 | 下载与生效策略 |
|---|---|
| 按钮、界面、控制面板 | 只更新 Desktop 和必要配套组件；退出后生效 |
| UE C++、飞控物理/碰撞修复 | 更新 UE/Workers 的兼容组合，不要求未变的城市资源重新下载 |
| 城市材质、建筑或地图 | 更新城市资源版本及其所需 UE 版本 |
| 用户设备、航线、参数 | 属于用户数据；升级只做可回退的格式迁移，不当作发布资源覆盖 |

组件清单记录 `release_id`、组件版本、依赖范围、协议版本、配置 schema、UE 内容构建基线、平台、大小、下载地址和 SHA-256；清单做发布签名，客户端仅持公钥，发布私钥不随程序分发。HTTPS、哈希和清单签名各自承担传输、完整性及发布者校验，不能只依靠下载成功判定可运行。

城市等大文件采用可恢复下载。**UE 资产分块**与**HTTP 下载分块**是两个层次：前者用于划分资源归属，后者可暂定 256–512 MiB 下载单元并保存下载进度。不能把下载文件简单切块后就宣称具备 UE 资产级差分更新。

UE 资源建议分为通用资产、基础场景、CitySample 场景等逻辑 Chunk。实际 Pak/IoStore 容器生成方式以本工程 UE 5.8.4 Cook 验证为准；如采用 IoStore，`.utoc/.ucas` 及相关 `.pak` 必须作为同一兼容集合处理，不能只替换其中一个文件。

### 第一版更新器

1. 启动后异步检查 stable 清单；网络不可用时继续运行本地已验证版本，不阻塞工作台。
2. 展示版本说明、实际下载量及所需空闲空间，可后台下载。
3. 检查断点文件的长度、哈希、签名和组件兼容性，发现缺包只补缺包。
4. 仿真期间不替换 UE、worker 或容器。提示结束仿真后更新，绝不因升级自动中断正在飞行的无人机。
5. 独立 Updater 等主进程和所有关联子进程退出，将新文件放到新版本目录。
6. 在同一卷完成写入、校验和落盘后切换版本指针；启动握手失败则回退到上一兼容组合。用户配置迁移先备份，回退时同时使用相容配置。
7. 保留一个可用旧版本，确认新版本通过运行检查后再回收无引用容器与下载缓存。卸载资源时先检查场景依赖。

第一版按“变更组件/容器完整替换 + 未变组件复用”实现，不承诺所有补丁都很小。城市容器整体改变时仍可能下载大量数据。第二版再建立稳定 Cook 基线、保留已发布 AssetRegistry/容器与构建清单，验证 UE 资产补丁或内容块复用；引擎/插件/序列化变化时允许重下兼容资源集。

### 发布渠道

推荐：GitHub 管代码与小型版本说明；HTTPS 对象存储/CDN 保存城市和正式更新文件。初期内测可用 GitHub Releases 存小包，但单个 asset 必须小于 2 GiB，几十 GiB 城市需要分片；访问体验仍需在两台电脑的实际网络测量。

离线交付提供 `Setup.exe + 资源数据分卷`，使用 Inno Setup；城市大包不强行塞入一个巨大 EXE。在线安装入口可以较小，仅负责安装基础运行程序及下载所选内容；其大小待构建统计。离线升级也读取同一签名发布清单，避免维护两套兼容规则。

MSIX/App Installer 本身也支持自动更新，但本项目首版选择安装器加独立更新器，以便管理大型可选城市内容、独立 UE 进程和离线交付；是否转用 MSIX 可在基本包验证后另行评估。

## 7. 实施顺序与验收

1. **构建发布基线**：锁定当前 UE 5.8.4、AirSim 固定提交与三个补丁、Qt/Python/native DLL 版本。检查资源软硬引用、运行插件及已知缺失源引用；不升级引擎、不改变当前用户 Fleet。
2. **基础独立包**：仅基础场景，完成 Game 构建、Cook、运行目录和自动启动；验证不调用编辑器、不依赖开发目录。
3. **城市独立包**：生成城市容器与完整大小报告；验证 World Partition 加载、道路碰撞、多设备、双模态尺寸、云台、手动/航线与真实旋翼。
4. **安装包**：干净机器、普通用户、不同安装目录、中文和空格路径、首次缓存与离线运行；发布目录只读情况下用户设置可保存。正式验收必须在没有 UE/VS/Python/Anaconda 的 Windows 机器或干净系统映像中完成，两台现有开发机测试不能替代此项。
5. **在线更新首版**：先验证仅界面更新不下载城市；再验证 UE 更新复用未变城市；网络中断可续传、坏包不激活、空间不足保留旧版、升级失败可回滚、用户航线/Fleet/录制不被覆盖。
6. **性能与发布**：城市连续运行至少30分钟，测源帧率、画面内容年龄、CPU/GPU/内存及场景加载时间；分别记录编辑器与独立包，不能把独立包上线等同低延迟优化通过。

每次发布保留源码提交、构建脚本、Cook/AssetRegistry 基线、组件清单、签名和测试报告。首个可交付里程碑是“另一台干净 Windows 安装后直接运行城市”，随后才是正式在线更新服务上线。
