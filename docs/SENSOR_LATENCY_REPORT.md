# 传感器延迟实测与使用建议

日期：2026-10-22。场景：City Sample 小城市；本机 UE 5.8.4、节能档；原始分辨率不变。

## 修复后的工作台预览（最新）

工作台改用 `camera.stream_frame` 读取UE异步缓存中的最新原尺寸JPEG。每个来源一条独立连接、最多一个在途请求，20Hz轮询上限；帧号和仿真采集时间不变时跳过解码和显示。Qt只保留一个待显示帧，忙时覆盖旧帧；重复源帧不会刷新“收到新帧”的计时，超过2秒显示过期。停订阅会中断网络读取，换源后的旧代响应不能显示到新设备。

RTSP继续作为对外H.264视频接口；工作台无需再把同一张JPEG经过H.264编码、MediaMTX和FFmpeg解码才能显示。RTSP网关也按源帧号去重，使用实际到达时间戳和passthrough，避免补帧。**下面的新延迟是原生工作台预览的数据，不是RTSP外部播放器延迟保证。** 外部播放器、跨机网络仍需单独测量；没有证明RTSP各内部队列的独立耗时。

同一个1600×1000工作台、同一时间码/PrintWindow方法，40秒复测：

| 画面 | 修复前中位 / P95 | 修复后中位 / P95 | 修复后最大值 | 独立源帧/秒 |
| --- | ---: | ---: | ---: | ---: |
| 可见光1920×1080 | 843 / 1923ms | **205 / 269ms** | 311ms | 9.65 |
| 红外640×512 | 386 / 535ms | **184 / 251ms** | 286ms | 10.00 |
| UE观察960×540 | 451 / 602ms | **187 / 271ms** | 341ms | 8.03 |

795次窗口采样，三路校验全部通过；没有另开视频订阅。表中仍为窗口持有的内容年龄，包含等下一帧的时间和约11ms窗口抓取开销。只看每个新时间码第一次被窗口观测到的时刻，中位分别为179/157/147ms。节能档源上限10/10/8Hz；没有通过缩小1080p/640×512画面降低延迟。

另开仪表窗口的40秒绘制测试，可见光时间码到Qt实际paint中位148/P95187/最大221ms，IR132/179/193ms，观察124/184/211ms。这组是新帧绘制口径，与上表持续内容年龄不能混算。证据：`sensor_end_to_end_latency_20261022.json` 的 `native_preview_candidate_40s`，以及 [正式窗口修复后40秒](evidence/sensor_existing_window_latency_20261022_native_after_40s.json)。

再做120秒正式单窗口测试：2382次采样/每路，无校验失败。VIS内容年龄中位206/P95271/最大330ms；IR189/251/293ms；OBS188/268/323ms，独立源约9.64/9.97/7.97Hz，没有出现原先秒级积压。EO/IR源时间差绝对值中位0、P95101、最大140ms，仍不能视为硬同步。证据：[120秒单窗口](evidence/sensor_existing_window_latency_20261022_native_after_120s.json)。测试期间后台有短暂Qt离线布局回归，没有另增视频订阅；不等于30分钟稳定性或高画质、多设备验收。

点云走独立JSON查询。有界轮询从200ms改为100ms，每设备最多一个在途请求，仅对显示中的点云生效；不修改激光扫描频率或物理仿真。最终额外仪表窗口40秒/54次靶位移，变化到实际绘制中位160/P95248/最大532ms，有366次有效点云更新；原310/494/807ms。原窗口从RTSP转为原生预览也改变负载，不能将改善全部归因于轮询间隔。同期VIS新帧paint中位142/P95183ms、IR125/168ms、OBS124/176ms。证据：`sensor_end_to_end_latency_20261022.json` 的 `native_final_points_40s`。

回归：44项核心/AirSim单元、4项Qt预览回归（重复帧过期、慢GUI单帧邮箱、切设备旧响应隔离、尺寸错误与恢复）、150%离线界面4组均通过。三路RTSP各解码3秒，31/32/25帧、H.264及原尺寸正确，见 [RTSP输出验证](evidence/rtsp_after_preview_fix_20261022.json)；这不是RTSP延迟测量。临时69个Actor已清理，测试桥关闭，未保存地图。

普通启动方式不变。更新代码后重开桌面；RTSP网关改动需重启网关。UE原生代码、地图和设备尺寸没有为本次修复修改，不需要重编UE。双模态仍不是同一采集时刻的硬同步帧，算法融合应继续使用明确的时间戳和同步策略。

## 修复前的诊断记录（历史基线）

以下内容描述本次修复前的问题与取证，不代表修复后的工作台状态。

## 日常单窗口复测

在已经运行的 WISEYE 窗口中观测40秒，没有另开播放器或解码器。每50ms用PrintWindow读取同一窗口的实际图像内容，解析UE场景内渲染的时间码；三路794次采样全部通过校验。表中“内容年龄”指当时窗口持有的图像所对应的UE测试标记有多旧，包含新帧之间继续显示上一帧的时间。

| 画面 | 内容年龄中位数 | P95 | 最差样本 | 观测到的独立源帧/秒 |
| --- | ---: | ---: | ---: | ---: |
| 可见光1920×1080 | **843ms** | **1923ms** | **2685ms** | 4.83 |
| 红外640×512 | 386ms | 535ms | 664ms | 7.53 |
| UE观察960×540 | 451ms | 602ms | 724ms | 6.83 |

P95表示95%的样本不超过该值。这是本机、该场景与当时负载下的实测，不是所有场景的固定延迟或帧率承诺。窗口捕获本身中位耗时11.2ms、P95为17ms，轮询间隔50ms；它不是精确的首次绘制时刻或显示器扫描输出测量。

若只统计每个新时间码第一次在窗口被观测到的时刻，中位分别为674/338/392ms；仍明显慢于只测视频传输时的约0.1秒。两种统计口径不能混用。

同一窗口采样中，可见光比红外的源时间码中位落后407ms；两路源时间差绝对值P95为1596ms，最大2199ms。**当前双模态画面不是同步帧，不能按同时到达或同时显示直接做融合。**

证据：[单窗口实测JSON](evidence/sensor_existing_window_latency_20261022.json)。

## 分段诊断与点云

另使用一个带绘制计时的真实MainWindow做了60秒云台运动测试，以及40秒分段测试；原窗口和UE仍运行，属于额外负载条件，与上面的单窗口测试不可直接相减。

| 检查项 | 中位数 | P95 | 说明 |
| --- | ---: | ---: | --- |
| UE可见光JPEG直接读取 | 142ms | 204ms | 绕过H.264/RTSP/桌面解码，仅诊断源链路 |
| 同轮可见光RTSP到Qt绘制 | 641ms | 1282ms | 最大1700ms，额外测试窗口运行中 |
| 同轮红外RTSP到Qt绘制 | 262ms | 335ms | 原始640×512 |
| 同轮观察RTSP到Qt绘制 | 348ms | 459ms | 原始960×540 |
| 点云目标实际位移到Qt绘制 | 310ms | 494ms | 54次位移，最大807ms；另有192次有效点云更新 |

点云使用运行时的查询碰撞靶，每750ms改变实际位置，通过现有LIDAR扫描、原有200ms界面轮询与真实LidarView绘制匹配位置变化；不走RTSP。这里测的是变化响应，不能当作每一个点的独立采集年龄。生产协议目前缺少可直接绑定到当前显示点云的扫描序号/采集时间戳。

分段证据表明：UE源图像并非始终滞后数秒，**可见光在后续编码、RTSP、解码和客户端处理链路中出现了额外积压**。具体是哪一个队列占主导仍需继续分段采样，不能只凭两组中位数把责任全部归给编码器、GPU或界面。额外窗口测试中，Qt收到图之后到绘制的中位开销约20～44ms，无法单独解释可见光的一两秒慢帧。

证据：[绘制与分段实测JSON](evidence/sensor_end_to_end_latency_20261022.json)。其中`city_economy_motion_60s`为60秒运动测试，`city_motion_stage_probe_40s`含直接JPEG与点云诊断。不同轮次、负载、端点不可直接当作同一条帧的分段延迟相加减。本轮直接JPEG的224次采样也包含预热期间，不能称为与40秒视频逐帧配对。

## 测量范围

临时标记在UE的pre-Slate回调更新，使用两进程共用的Windows QueryPerformanceCounter时钟；时间码真实经过场景渲染、GPU读回、JPEG、H.264/MediaMTX、RTSP解码与窗口绘制，不使用ping或“接收于多久前”替代延迟。标记带校验；点云靶仅阻挡Visibility查询，不参与无人机物理碰撞。

标记更新与仿真Tick/捕获并非硬件同步，存在约一帧级别的时序误差；统计不含显示器扫描输出，不含控制指令到达、飞控或机械响应。它能揭示场景变化到画面的滞后，不能直接当作操纵指令的完整响应时间。测试靶和时间码会增加少量场景负担，本轮不是零开销测量或跨机网络测试。

所有测试物体仅存在于当前PIE运行中，未保存地图；测试结束移除69个临时Actor，恢复测试前云台设置。无人机起降没有用于本次延迟测试。当前运行状态以用户实际操作为准，不自动降落或改变飞控任务。

## 正常使用时怎么判断

- **已连接**：网络连接正常。
- **UE正在推进**：仿真Tick继续变化，不保证画面够新。
- **接收于0.0s前**：本地刚收到一张图；它可能对应较早的UE时刻。
- **界面“新帧”Hz**：来自UE完成缓存的计数，不等于当前窗口实际显示的独立新图帧率，也不是延迟。

日常先等城市缓存完成，保留一个UE与一个桌面，只显示需要的来源；GPU负载高时使用节能档。遇到明显滞后，不要连续叠加操纵输入，应先确认画面与状态恢复。隐藏卡片能减少本地解码，但不等于停用传感器；暂停本地画面也不能让后台流自动停止。

原始画面仍保留1920×1080和640×512，不能通过只缩小预览就假定已经解决源链路延迟。高画质、更高编码帧率或更多播放器也不能直接证明更实时。

## 后续优化顺序

1. 优先定位并消除1080p通道的旧帧积压：分别测发布端写管道、编码输出、RTSP接收和解码输出；队列保持有界、过期帧丢弃。
2. 给图像贯穿源时间戳、frame_seq、run_id及设备身份，绑定到真正显示的帧，再在界面显示源图像年龄。不能拿最新UE状态的时间戳冒充正在显示图像的时间戳。
3. 为点云增加scan_seq、采集时间与扫描姿态，并保留有界最新扫描；评估200ms轮询与网络/绘制排队。
4. 按源时间对齐双模态数据，之后再评估GPU编码、减少复制和绘制开销；每一步重复相同场景的测量，保留原始分辨率。

本轮没有替上述优化设定“已经达到低于200ms”等结果；需要单独实施与复测。

普通运行无需执行本节。要求已打开城市PIE、PythonScriptPlugin启用，本机测试Python有PySide6/Pillow；不允许两套测试同时运行。
